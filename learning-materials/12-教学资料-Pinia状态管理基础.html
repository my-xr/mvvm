一、学习导读

1.1 本节定位：登录状态管不住

第 11 课我们用 localStorage 临时保存登录状态，路由守卫读它来判断是否登录。但它有两个毛病：不是响应式的（写入后，页面上显示用户名的地方不会自动更新），而且每个组件都要自己读写、自己解析。

请想象一个具体场景：页面顶部的 Header 要显示“当前用户”，登录页登录成功后，Header 应该立刻变化；退出登录时，所有用到用户信息的地方也要同时清空。这就是多个组件共享同一份数据的问题。

本节围绕它展开：先看现有办法为什么撑不住（K12-1），再用 Pinia 建一个共享仓库（K12-2），学会安全地修改和读取（K12-3），然后加上派生数据（K12-4）和集中的业务方法（K12-5）。

课程边界：本课的 store 只保存在内存中，刷新页面会丢失；状态持久化、多个 store、store 之间互相调用、$reset、$subscribe 在第 13 课讲；真实登录接口在第 14 课 Axios 中接入，本课用定时器模拟异步请求。

1.2 先修基础

先修知识程度说明
第 4 课 响应式（ref、computed）必须store 里的 state、getters 就是 ref 和 computed 的“共享版”
第 7 课 props / emits必须用来说明“组件通信”为什么在多层组件里不够用
第 9 课 provide / inject必须K12-1 中作为对比方案
第 11 课 导航守卫与 localStorage 登录必须本课的出发点，后续课程会把守卫改为读 store

1.3 学习目标

  • ✅ 能说清哪些数据该放 Pinia、哪些该留在组件里
  • ✅ 会安装并挂载 Pinia，用 defineStore 创建 store
  • ✅ 会在组件中读取、修改 state，并用 storeToRefs 解构
  • ✅ 会用 getters 表示派生数据，用 actions 封装业务逻辑（含异步）
  • ✅ 能创建 userStore，让登录状态在多个组件间同步

二、知识点详解

知识点 K12-1：为什么需要状态管理

场景与痛点

CTTS 的结构是：App → Layout → Header，同时 App → Layout → Login 页。登录页登录成功后，Header 要显示用户名，项目页也要根据角色显示按钮。登录页和 Header 不是父子关系，却要读写同一份用户信息。

笨办法

办法怎么做为什么撑不住
props + emit数据放到共同的祖先，逐层 props 向下传、emit 向上通知层级一深，中间组件被迫转发自己用不到的数据；兄弟组件之间要绕道祖先
provide / inject祖先 provide，后代 inject数据从哪里来、谁在改它不清楚，修改规则分散；缺少统一的调试工具
localStorage各组件自己读写不是响应式，写入后页面不会自动更新；每个组件各写一遍解析代码

核心思想

把共享的数据从组件里搬出来，放进一个所有组件都能直接访问的公共仓库；谁用谁自己去取，谁改了所有人自动看到。

定义

状态管理：把多个组件共享的数据（状态）放在组件之外统一存放、统一修改。Pinia 是 Vue 3 官方推荐的状态管理库。

最小示例：不用库也能“搬出来”

其实只靠第 4 课的 ref 就能理解这个思想：把 ref 定义在组件外面的 JS 文件里。

// src/shared/auth.js
import { ref } from 'vue'
export const token = ref('')   // 定义在组件外：所有导入它的组件共享同一个 ref
<!-- 任意两个组件都这样用 -->
<template><p>当前 token：{{ token || '未登录' }}</p></template>
<script setup>
import { token } from '../shared/auth'
</script>

预期现象：在一个组件里执行 token.value = 'abc'，另一个组件的页面立刻变化，不需要 props，也不需要 localStorage。

前后对照

逐层传递 / localStorage共享仓库
数据沿组件树走，中间层被迫参与组件直接取，和位置无关
localStorage 不响应响应式，改了即更新
读写代码到处都是集中在一个文件

应用场景与边界

  • 适合放进共享仓库：登录用户信息、权限、购物车、主题/语言、全局的项目列表缓存——多个页面都要读或改的数据。
  • 不适合：只有一个组件用的数据（表单草稿、弹窗开关、输入框内容）。不要什么都往仓库里放，否则仓库会变成难以维护的“全局变量堆”。
  • 父子之间简单的数据传递仍然用 props / emits，更直接。

易错点

  • 把所有数据都放全局：→ 原因：觉得“放哪都能用”；→ 做法：先问“有几个组件需要它”，只有一个就留在组件内。
  • 以为共享仓库能自动保存刷新：→ 内存里的数据刷新就没了，持久化是第 13 课的内容。

小结与钩子

共享数据放到组件之外统一管理，是状态管理的核心思想。但还剩一个问题：自己用 ref 搭出来的“仓库”没有统一的约定——数据放哪、怎么改、怎么调试、怎么分多个仓库，全靠自觉。下一节用官方的 Pinia 解决。

知识点 K12-2：第一个 store：defineStore 与 state

场景与痛点

K12-1 的方案能共享数据，但项目里会有用户、项目、任务等很多类共享数据。每类都零散地定义 ref，命名和修改方式各不相同，团队协作时很难统一，也看不到数据是什么时候被谁改的。

核心思想

Pinia 把每一类共享数据装进一个有名字的store（仓库）。store 是一个用 defineStore 定义的“可共享的小模块”，组件通过 useXxxStore() 取到它。

定义

  • createPinia()：创建 Pinia 实例，通过 app.use() 挂载到应用。
  • defineStore('id', 配置)：定义 store。第一个参数是全局唯一的 id，第二个是配置对象。
  • state：store 的数据，写成返回对象的函数。

最小示例

npm install pinia
// src/main.js
import { createApp } from 'vue'
import { createPinia } from 'pinia'
import App from './App.vue'

createApp(App).use(createPinia()).mount('#app')
// src/stores/user.js
import { defineStore } from 'pinia'

export const useUserStore = defineStore('user', {
  state: () => ({ token: '', userInfo: null })   // 数据：函数返回对象
})
<!-- Header.vue：读取 -->
<template><span>{{ userStore.token || '未登录' }}</span></template>
<script setup>
import { useUserStore } from '../stores/user'
const userStore = useUserStore()
</script>

<!-- Login.vue：修改 -->
<template><button type='button' @click='login'>登录</button></template>
<script setup>
import { useUserStore } from '../stores/user'
const userStore = useUserStore()
const login = () => { userStore.token = 'abc' }
</script>

预期现象：点击登录页的按钮，Header 里的文字立刻从“未登录”变成 abc。两个组件互不相识，却共享同一份数据。

前后对照

K12-1 的 ref 仓库Pinia store
自己约定文件和命名defineStore('user', ...) 统一结构，id 即名字
只有一个 ref一个 store 可以装多份状态，并扩展出 getters、actions
难以调试支持 Vue Devtools，能看到 state 变化

应用场景与边界

  • 一类共享数据对应一个 store，例如 user、project，多个 store 的组织在第 13 课。
  • store 文件放在 src/stores/，文件名与 id 保持一致，导出函数命名为 useXxxStore。

易错点

  • 忘记 app.use(createPinia())：→ 报“getActivePinia was called with no active Pinia”；→ 在 main.js 挂载。
  • state 写成对象而不是函数：→ state: { token: '' } 是错误的，必须 state: () => ({ token: '' })，这样每个应用实例的数据才互相独立。
  • 两个 store 用了相同的 id：→ 会互相覆盖；→ id 必须唯一。

小结与钩子

createPinia 挂载，defineStore 定义，state 存数据，组件里 useUserStore() 取用。但还剩一个问题：上面的写法是直接 userStore.token = 'abc' 修改，修改方式有几种、各适合什么场景？解构取值又为什么会失去响应？下一节解决。

知识点 K12-3：修改 state 与 storeToRefs

场景与痛点

登录成功后要同时更新 token 和用户信息两个字段；模板里写 userStore.userInfo.username 太长，想解构成 username 直接用，结果发现修改后页面不更新了。

核心思想

store 是一个响应式对象：通过 store 访问，永远是活的；一旦把值“拿出来”成普通变量，就断了联系。

定义：几种修改方式

方式写法适合
直接改userStore.token = 'abc'改一个字段，简单直接（Pinia 允许）
$patch 对象userStore.$patch({ token: 'abc', userInfo: { username: 'tom' } })一次改多个字段
$patch 函数userStore.$patch(state => { state.token = 'abc' })需要修改数组、复杂逻辑
actionuserStore.login(...)带业务规则，见 K12-5

最小示例：解构与 storeToRefs

<template>
  <p>错误解构：{{ badToken }}</p>
  <p>正确解构：{{ token }}</p>
  <button type='button' @click="userStore.$patch({ token: 'new-token' })">批量修改</button>
</template>
<script setup>
import { storeToRefs } from 'pinia'
import { useUserStore } from '../stores/user'

const userStore = useUserStore()
const { token: badToken } = userStore       // 普通值：以后不再更新
const { token } = storeToRefs(userStore)    // ref：保持响应式
</script>

预期现象：点击按钮后，“正确解构”显示 new-token，“错误解构”仍停留在原值。

应用场景与边界

  • 只改一个字段：直接改；改多个字段：$patch；涉及校验、请求或多个字段联动：写成 action（K12-5）。
  • Pinia 允许组件直接改 state，这是语法能力，不代表应该到处改。规则散落在各组件里，以后很难找。
  • storeToRefs 只用于 state 和 getters；方法（actions）不是响应式数据，直接从 store 解构即可：const { login } = userStore。

易错点

  • 直接解构 state：→ 得到的是普通值，不再响应；→ 用 storeToRefs，或始终写 userStore.token。
  • 在脚本里忘了 .value：→ storeToRefs 得到的是 ref，在 <script> 里要写 token.value，在模板里则自动解包。

小结与钩子

改 state 有直接改、$patch、action 三类；取值要么通过 store 访问，要么用 storeToRefs 解构。但还剩一个问题：“是否已登录”这种数据是由 token 推出来的，每个组件都写一遍 !!userStore.token，一旦判断规则变了（比如 token 为空串或 null），所有组件都要改。下一节用 getters 把派生数据集中起来。

知识点 K12-4：getters 派生状态

场景与痛点

Header 要显示“你好，张三”，项目页要判断是否已登录，菜单要判断是否管理员。这些都是从 token、userInfo 推出来的，如果每个组件各写一遍，判断规则重复，改一处漏一处。

核心思想

getters 就是 store 里的 computed：规则写一次，所有组件直接用，依赖的数据不变就用缓存。

定义

getters 是基于 state 计算出的派生值，参数是 state；有缓存；使用时像属性一样读取，不加括号。

最小示例

export const useUserStore = defineStore('user', {
  state: () => ({ token: '', userInfo: null }),
  getters: {
    isLogin: (state) => !!state.token,
    username: (state) => state.userInfo?.username || '未登录',
    // 访问其他 getter 要用 this，所以这里必须写成普通函数
    greeting() {
      return '你好，' + this.username
    }
  }
})
<template>
  <p>{{ userStore.greeting }}</p>
  <p v-if='userStore.isLogin'>已登录</p>
</template>
<script setup>
import { useUserStore } from '../stores/user'
const userStore = useUserStore()
</script>

预期现象：未登录时显示“你好，未登录”；给 userStore.userInfo 赋值后，问候语自动变成用户名。

前后对照

每个组件自己算getters
判断规则重复多处规则只写在 store
规则变化要改多处改一处即可
每次都重新计算依赖不变时用缓存

应用场景与边界

  • 适合：是否登录、是否管理员、列表过滤结果、统计数量、拼接后的显示名称。
  • getters 只负责“算出来”，不要在里面修改 state；要修改请用 action。
  • 只有一个组件用到的小计算，直接在该组件里写 computed 即可。

易错点

  • getter 里用箭头函数又想用 this：→ 箭头函数的 this 不指向 store；→ 访问其他 getter 时写普通函数。
  • 把 getter 当函数调用：→ userStore.isLogin() 报错；→ 直接读 userStore.isLogin。
  • getter 依赖外部变量：→ 外部变量变化时不会触发更新；→ getter 只依赖 state 和其他 getter。

小结与钩子

getters 是 store 的 computed，集中派生规则、带缓存。但还剩一个问题：登录并不只是“给 token 赋值”，还要校验用户名、请求接口、保存用户信息、出错处理。这些步骤如果散在登录页里，Header、守卫、退出登录各写一套，很快对不上。下一节用 actions 集中业务逻辑。

知识点 K12-5：actions 封装业务

场景与痛点

登录需要：校验输入 → 发请求（异步）→ 成功后同时写 token 和用户信息；退出需要同时清空两项。如果这些步骤写在 Login.vue 里，别的组件想退出登录时只能复制一遍。

核心思想

actions 就是 store 里的方法：把“怎么改数据”连同业务规则一起放进仓库，组件只负责调用，不关心细节。

定义

actions 是 store 的方法，可以同步也可以异步（async），通过 this 访问 state、getters 和其他 actions。

最小示例

export const useUserStore = defineStore('user', {
  state: () => ({ token: '', userInfo: null }),
  actions: {
    // 同步
    logout() {
      this.token = ''
      this.userInfo = null
    },
    // 异步：用定时器模拟网络请求，第 14 课换成真实接口
    async login(credentials) {
      if (!credentials.username) throw new Error('请输入用户名')
      await new Promise((resolve) => setTimeout(resolve, 500))
      this.token = 'fake-token-' + Date.now()
      this.userInfo = { id: 1, username: credentials.username, role: 'admin' }
    }
  }
})
<script setup>
import { useUserStore } from '../stores/user'
const userStore = useUserStore()

const onLogin = async () => {
  try {
    await userStore.login({ username: 'tom' })   // 异步 action 要 await
  } catch (e) {
    alert(e.message)
  }
}
</script>

预期现象：点击登录约 0.5 秒后，Header 显示用户名；传空用户名时弹出“请输入用户名”，state 不会被修改。

前后对照

组件里直接改 stateaction
登录逻辑只在登录页任何组件调用 userStore.login 都一致
多个字段联动容易漏改一个方法里统一改完
难以统一处理错误错误规则写在 action 里

应用场景与边界

  • 适合：登录/退出、加入购物车、请求列表并保存、涉及多个字段联动的修改。
  • 简单到一行的赋值（比如切换主题颜色），直接改 state 或 $patch 就够了，不必为每个字段都写 action。
  • action 不是 getter：它可以修改 state、可以异步；getter 只能读和计算。

易错点

  • actions 里用箭头函数：→ this 指向错误，取不到 state；→ 用方法简写 login() { ... }。
  • 异步 action 忘了 await：→ 登录还没完成就继续执行，读到的仍是旧状态；→ 调用处 await，并用 try/catch 处理异常。
  • action 出错却没人处理：→ 异常默认会向上抛出；→ 在调用处 catch 并提示用户。

小结

actions 是 store 的方法，用 this 访问数据，可同步可异步，让业务规则集中在仓库里。至此 userStore 具备了数据（state）、派生（getters）、行为（actions），下面把它们整合到 CTTS 里。

三、综合示例：CTTS userStore

3.1 从零运行

本例新建一个小项目，把 K12-1 的痛点真正解决掉：登录页登录后，Header 无需刷新立即显示用户名；退出后立即恢复“未登录”。

  1. 创建项目并安装 Pinia（命令见下）。
  2. 按 3.2 创建文件，覆盖 src/main.js、src/App.vue。
  3. 执行 npm run dev，输入用户名点击登录：约 0.5 秒后 Header 显示用户名和“退出”按钮。
  4. 不输入用户名直接登录：弹出错误提示，Header 不变。
  5. 点击退出：Header 立即恢复“未登录”。
  6. 登录后刷新页面：状态消失，这是预期的，也是第 13 课持久化要解决的问题。

cd ctts-pinia

src/main.js：

import { createApp } from 'vue'
import { createPinia } from 'pinia'
import App from './App.vue'

createApp(App).use(createPinia()).mount('#app')

src/stores/user.js：state、getters、actions 三者齐全。

import { defineStore } from 'pinia'

export const useUserStore = defineStore('user', {
  state: () => ({
    token: '',
    userInfo: null
  }),
  getters: {
    isLogin: (state) => !!state.token,
    username: (state) => state.userInfo?.username || '未登录',
    role: (state) => state.userInfo?.role || 'guest'
  },
  actions: {
    async login(credentials) {
      if (!credentials.username) throw new Error('请输入用户名')
      // 简化：用定时器模拟请求，真实接口在第 14 课接入
      await new Promise((resolve) => setTimeout(resolve, 500))
      this.token = 'fake-token-' + Date.now()
      this.userInfo = { id: 1, username: credentials.username, role: 'admin' }
    },
    logout() {
      this.token = ''
      this.userInfo = null
    }
  }
})

src/components/Login.vue：

<template>
  <form @submit.prevent='onLogin'>
    <input v-model='form.username' placeholder='用户名' />
    <input v-model='form.password' type='password' placeholder='密码（本课不校验）' />
    <button type='submit'>登录</button>
  </form>
</template>
<script setup>
import { reactive } from 'vue'
import { useUserStore } from '../stores/user'

const form = reactive({ username: '', password: '' })
const userStore = useUserStore()

const onLogin = async () => {
  try {
    await userStore.login(form)
  } catch (e) {
    alert(e.message)
  }
}
</script>

src/components/UserHeader.vue：

运行结果检查：Login 与 UserHeader 没有父子关系，也没有 props 或 emit，登录后 Header 却立即更新，说明两者共享了同一个 store；规则（是否登录、显示名、登录和退出）全部集中在 user.js 里。对比第 11 课的 localStorage 方案：那里写入后 Header 不会自动更新。刷新页面后状态消失，下一课解决。真实项目不要在前端保存密码，令牌安全需要后端与 HttpOnly Cookie 等方案共同设计。

四、拓展阅读（选学）

  1. 组合式写法（Setup Store）：defineStore('user', () => { const token = ref(''); const isLogin = computed(() => !!token.value); const login = (t) => { token.value = t }; return { token, isLogin, login } })。ref 对应 state，computed 对应 getters，函数对应 actions，与选项式等价，更灵活。
  2. Pinia 与 Vuex：Vuex 是 Vue 2 时代的状态库，Pinia 是它的继任者，主要区别如下表。
  3. 下一课内容：状态持久化（刷新不丢）、多个 store、store 之间互相调用、$reset 和 $subscribe。
